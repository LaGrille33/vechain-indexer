  It does not fetch production data or start a backfill. If a build/start fails,

    sudo sh /volume1/docker/vebetter-scoring-pilot/scripts/install-nas.sh
  This resumes the existing project/password. Do not rerun the fresh extraction.
  Synology requires the database bind-source directory to exist before startup.
  If the first uploaded installer reports data/postgres does not exist, run:
    sudo mkdir -p /volume1/docker/vebetter-scoring-pilot/data/postgres
    sudo sh /volume1/docker/vebetter-scoring-pilot/scripts/install-nas.sh

Public-mainnet backfill (operator starts it AFTER the update)
  Uses HTTPS public mainnet chain/indexer endpoints; no API keys, signing keys
  or VeCarbon database credentials are required. It writes only the NAS pilot.
  Historical app populations and exact allocations are read at finalized round
  boundaries. Reward events supply exact amounts, wallets and action counts.
  Event order follows EmissionDistributed/V2, including within-block positions,
  matching the official indexer's cycle boundaries. Zero-activity apps remain.
  Public indexer totals are a separate diagnostic check: counts must match and
  financial differences must fit its floating-point precision tolerance.
  Source failures or mismatches fail the job rather than substituting zeros.

  Initial SMALL pilot, detached so leaving SSH does not stop it:
    sudo docker compose -f /volume1/docker/vebetter-scoring-pilot/compose.yaml exec -d engine sh -c 'node src/job.mjs chain mainnet 1 3 >> /logs/launcher.jsonl 2>&1'
  Follow /progress and verify its report before the full range:
    sudo docker compose -f /volume1/docker/vebetter-scoring-pilot/compose.yaml exec -d engine sh -c 'node src/job.mjs chain mainnet 1 latest >> /logs/launcher.jsonl 2>&1'
  Run ONE job at a time. A new job from 1 reuses committed source pages; identical
  snapshots/runs are reused when input and calculation versions match.
  'latest' is resolved once, to the last completed round at a finalized anchor.
  No perpetual schedule is installed and no live incomplete round is scored.

  Job UUIDs are printed in data/logs/launcher.jsonl and shown at /progress.
  Resume a failed/stale job with its UUID (same pinned plan/cursor):
    sudo docker compose -f /volume1/docker/vebetter-scoring-pilot/compose.yaml exec -d engine sh -c 'node src/job.mjs chain mainnet 1 latest JOB_UUID >> /logs/launcher.jsonl 2>&1'
  Replace JOB_UUID with the real UUID. Do not resume an actively running job.
  Detached jobs survive an SSH disconnect, but container/NAS restarts require
  this explicit resume. There is no automatic whole-job retry daemon.

  Per-page wallet aggregates and source cursors commit atomically in Postgres.
  Full first-seen history is claimed only after all rounds from 1 are scanned;
  round 1 also scans earlier chain history and retains pre-round-1 first-seen
  entries as round 0. New users means first rewarded interaction per app.
  Starting at a recent round leaves new_users null and yields only /51 report
  subtotals. Do not use the diagnostic API's rounded financial values as inputs.
  Source caches retain wallet-level aggregates locally (not proof payloads).
  They are private data and excluded from shared HTML/JSON reports and bundles.

Prepared-snapshot ingestion
  Optional normalized files are still supported. Navigator first-seen archives
  need their own shard/completeness/cutoff audit before reuse.

  Put normalized JSON snapshots in data/imports. Required structure:
    network: mainnet or testnet
    round_id: integer
    source_block_number: nonnegative integer STRING
    source_block_id: 0x + 64 lower-case hex characters, from the real checkpoint
    round_end_timestamp: Unix seconds, integer
    new_user_history_complete: boolean, false until history is actually verified
    source_manifest: object recording source, retrieval time, coverage proof,
                     historical membership evidence and indexer checkpoints
    app_ids: complete historical on-chain list, including apps with zero activity
    metrics: array of objects with app_id plus STRING fields active_users,
             actions, allocated, distributed, and new_users as STRING or null

  Amounts are human B3TR units with up to 18 decimal places. Counts must be
  integer strings to preserve values beyond JavaScript's safe integer range.
  Unknown new users stay null. Each app must appear exactly once. The importer
  checks shape/membership consistency; it cannot independently prove that your
  supplied on-chain list or coverage assertion is true. The source extractor
  and reconciliation must establish that before new_user_history_complete=true.

  docker compose exec -T engine node src/job.mjs import /imports/round-96.json
  docker compose exec -T engine node src/job.mjs list
  docker compose exec -T engine node src/job.mjs execute RUN_UUID

  Alternatively, run 'node src/job.mjs next' inside the engine to process one
  pending run. No schedule is installed. Incomplete snapshots are saved without
  creating a run. A complete import registers a run but does not execute it.
  Canonical input hashes and hashed calculation code identify snapshots/runs.
  Identical imports reuse the same snapshot/run; completed executions are
  idempotent. Corrections create new versions; frozen history is not overwritten.
  The web execution endpoint defaults disabled. Use the manual CLI initially.

HTML calculation reports
  docker compose exec -T engine node src/job.mjs report mainnet 96
  docker compose exec -T engine node src/job.mjs report-all mainnet

  The first command exports every app in the newest saved round-96 snapshot.
  The second exports every saved mainnet round, choosing its newest snapshot.
  Testnet is a separate selector: never combine its ranks with mainnet.
  No 200-app display limit applies. Files are saved under data/exports with
  unique names: an offline HTML report and an exact-decimal JSON companion.
  Existing files are not overwritten. No external scripts or assets are needed.

  Reports include raw metrics, app labels when source_manifest.app_names is
  supplied, app IDs, per-metric below/tie counts and percentiles, activity
  weights, full-precision allocation/distribution strings, efficiency capped at
  one, weighted contributions, competition ranks and source/run/code hashes.
  Financial precision is exactly that of the saved input, not an assertion that
  the original API supplied on-chain 18-decimal precision. Verify source precision.

  With verified new-user history, report scores match the current Kotlin rule
  and are compared with an attached completed run when one exists. A report
  made from unexecuted inputs says that it is not a saved full scoring run.
  Without verified history, the new-user percentile/term is excluded for ALL
  apps in that round; Active Wallets and Actions retain weights 0.5 and 0.2.
  Their partial Activity maximum is 70, weighted at 30% (maximum 21), plus
  Distribution weighted at 30% (maximum 30): available subtotal maximum 51.
  No rescaling to 100, invented new-user zeros or full-reputation rank is shown.
  Full Activity/Distribution has maximum 60. Profile/Community remain excluded
  because this package has no approved inputs/calculators for them.
  Incomplete app populations withhold percentiles, scores and rankings.

  Missing-new-user partial results are report artifacts only; the existing full
  scoring_run API remains strict and still requires complete new-user history.
  Reports use a read-only repeatable-read DB transaction. They read saved
  snapshots, not production source tables. Arbitrary source manifests, database
  connection details and wallet records are not included in report exports.
  Report generation reads stored inputs; the separate blockchain runner fetches
  source history and records its coverage evidence.

Progress monitoring and round-by-round processing
  Open http://localhost:8788/progress through the same private SSH tunnel.
  It refreshes every 5 seconds and shows phase, current round, completed/total
  rounds, source kind, processed records, source units, retries, elapsed time,
  last heartbeat, rough remaining-time range and approximate completion time.
  An HTML report link appears when report generation finishes. No job displays
  as a running blockchain backfill just because the tracker exists.

  The ETA uses the last five successfully completed rounds, after at least
  three timings exist. It adjusts for elapsed work on the current round. It is
  a rough estimate, not a deadline: round sizes, first-seen work and retries vary.
  A 15-second heartbeat supports stale detection; after 45 seconds without one,
  ETA is withheld. Reporting is a separate finalization phase, so 100% of rounds
  does not claim that the entire job/report is already finished.

  Both blockchain and optional prepared-file batches update this page. For
  blockchain jobs units are fetched event pages, records are source event logs;
  a page total is unknown until the round scan finishes. App metadata lookups
  and reconciliation can take time while record counters stay unchanged.
  Retries counts repeated round attempts, not individual HTTP request retries.
  Up to four public HTTP retries use backoff. A failed job needs manual resume.
  Page-level cache checkpoints avoid downloading committed pages again.

  The following optional runner consumes already prepared snapshot files;
  its units are files and its records are app metric rows.
  Create a JSON plan under data/imports with this structure:
    {"network":"mainnet","rounds":[
      {"round":96,"file":"/imports/round-96.json","sha256":"REPLACE_WITH_FILE_SHA256"},
      {"round":97,"file":"/imports/round-97.json","sha256":"REPLACE_WITH_FILE_SHA256"}
    ]}
  Use the SHA-256 of each complete input file, e.g.:
    sha256sum data/imports/round-96.json
  The driver validates each file hash and its network/round before importing.

  Start (prints a job UUID immediately):
    docker compose exec -T engine node src/job.mjs process /imports/plan.json
  Inspect while it runs, from another terminal:
    docker compose exec -T engine node src/job.mjs status JOB_UUID
  Resume the same job after a failure/restart:
    docker compose exec -T engine node src/job.mjs process /imports/plan.json JOB_UUID

  Job state, counters and per-round checkpoints live in Postgres, not in the
  browser. A round's import/calculation and completion checkpoint commit in
  one transaction. Resume skips completed rounds. Prepared files are reread for
  unfinished rounds; blockchain rounds resume the committed page cursor.
  The exact same plan/file hashes are required. For corrected inputs start a
  new job/snapshot version. A per-job direct-Postgres session lock prevents two
  workers from running the same job; session-lock behavior and multiple real
  connections still need verification on the deployed server (WASM tests do not
  establish real Postgres concurrency). No automatic retry loop is installed.

  Logs: data/logs/backfill-JOB_UUID.jsonl (mounted at /logs). Follow them with:
    tail -f data/logs/backfill-JOB_UUID.jsonl
  Rotation keeps current + two previous files, at about 5 MB each. Logs contain
  controlled phase/events and round IDs, not credentials, source payloads or
  arbitrary exception messages. Postgres is the authoritative recovery state.
  Ensure the container's node user (UID 1000) can write data/exports and
  data/logs on the NAS; inspect actual DSM ACLs before changing permissions.

Storage and backups
  data/postgres: database files, including durable source cursors, per-app/wallet
  ledgers, immutable snapshots, scoring runs/results and progress. Do not copy
  these live as a backup.
  data/imports: normalized source snapshots; preserve alongside provenance.
  data/exports: HTML/JSON reports and future rollout handoff files.
  backups: pg_dump custom-format files produced by 'sh scripts/backup.sh'.
  Backups are not automatically scheduled or deleted. Before relying on them,
  restore a dump into a separate scratch database and compare row counts and
  saved input hashes. Keep an additional copy off this NAS. Never restore over
  a running database as a test.
